# orchestrate-mode · 编排手册

> SKILL.md 的细节附录。只在需要判定分级、选 agent、写指令或核对汇报格式时读取。

---

## 1. 分级矩阵

**判定方式**：任一条件命中即归入该级；命中多级取最高。

> 「执行吧 / 可以 / 确认 / 确认方案 / 执行开发 / 进行开发」等确认类指令只说明**允许开工**，分级仍按本表判定，**不因确认词自动升级为 L2**。

| 级别 | 判定（任一） | 做法 | 典型例子 |
|---|---|---|---|
| **L0 直达** | 单文件；≤30 行；无外部检索；一次改完即可自查 | 主对话直接改 + 自查，**不派 agent** | 改错字、调参数、加一行日志、改一段文案 |
| **L1 单兵** | 2–3 个文件且同模块；或单一明确检索问题；一次 Explore 可答 | 派 1 个 agent，主对话验收 | 同一页面改样式 + 文案；查清一个 API 的用法 |
| **L2 编排** | ≥3 文件；跨模块 / 跨层；多源研究；子任务可并行；预计 ≥10 轮工具调用 | 拆 DAG + 多 agent 并行 / 串行 | 新增功能（前端 + 后端 + 数据）、主题调研并出报告、批量改 10 个页面 |

**边界补充**

- 同构批量（10 个文件同样的改法）→ 交给**一个** agent 顺序做，不拆 10 个。
- 需求本身模糊 → 先用 Orchestrator / Plan 把需求变成可执行指令，再按 L2 拆。
- 改完要「顺手」重构无关代码 → 不允许，另开任务。

## 2. Agent 路由

| 任务形态 | 首选 agent | 备注 |
|---|---|---|
| 代码库结构、概念搜索、跨文件关系 | **Explore** | 只读；返回结论，不写码 |
| 明确的多步编码、批量改造 | **general-purpose** | 可读写，需给文件边界 |
| API / 数据库 / 后端架构设计 | **backend-architect** | 设计类任务 |
| 前端页面视觉与交互验收（有 URL） | **browser_use** | 必须给 http(s) URL；最多 3 个/次 |
| 需要实施计划、技术方案比较 | **Plan** | 只读规划，不落地 |
| 需求还很模糊、需要压成行动指令 | **Orchestrator** | 只产指令块，**不能再派 agent** |
| 大规模外部资料检索 | general-purpose（WebSearch / WebFetch）或 research 插件 | 要求来源 URL + 日期 |
| 文档 / 报告写作 | general-purpose | 指定风格、事实纪律、产出路径 |

**选型原则**

- 探索类一律先 Explore，拿到结论再决定是否派写码 agent（scout-then-execute）。
- 写码 agent 一次只负责一个可独立验收的模块。
- 审查 / 复核另派一个 agent，**不要**让实现者自证。

## 3. 指令模板

### 3.1 开发型

```
背景：<为什么做、属于哪个任务、上下游是什么>
目标：<可验收的结果，不写「优化一下」>
验收：<运行哪个命令 / 检查哪些文件 / 什么算完成>
已知：<已确认的结构、已排除的方案、相关文件路径与行号>
范围：允许改 <目录/文件>；禁止碰 <文件/目录>
约束：<项目规则、平台约定（如 Windows PowerShell 用 ; 不用 &&）、命名与缩进、只读或可写>
产出：改动文件清单 + 验证命令 + 实际输出
禁止：不重构无关代码、不加未要求的功能、不提交、不发布
```

### 3.2 研究型

```
问题：<要回答的具体问题，拆成 3–5 条>
时间窗口：<如近 12 个月>
来源要求：每条结论附 URL + 发布日期 + 原文摘录；优先一手来源
输出：结论 + 证据 + 不确定性（哪些没查到、哪些存疑）
禁止：编造数字；把二手转述当一手；把推测写成事实
```

### 3.3 审查型

```
范围：<分支 / 文件 / 目录>
基准：<对比对象，如 main 分支、上一版>
关注点：<正确性 / 边界 / 性能 / 安全 / 风格>
输出：问题 + 位置（文件:行）+ 严重度 + 建议；只读，不改文件
```

**通用纪律**：给背景和目标，不只给窄步骤；不写「根据你的发现去修」这类把理解外包的句子。

## 4. 编排形态

| 形态 | 适用 | 做法 |
|---|---|---|
| **Fan-out 并行** | 子任务互不依赖、文件不重叠 | 同一批同时发出，收口统一验证 |
| **Pipeline 串行** | 后一步依赖前一步产出 | 研究 → 计划 → 实现 → 验证，逐段推进 |
| **Scout-then-execute** | 结构不明 | 先 Explore 摸清结构，再给写码 agent 精确指令 |
| **Background** | 长任务，且主对话有其他可做的事 | 后台运行，不轮询、不空等 |
| **Resume** | 任务被中断且仍需同一目标继续 | 带上原 agent ID 续跑，不重开新 agent |

**失败处理顺序**：补信息重派 → 换 agent 类型 → 降级为主对话自己做。**不重复同一条指令**。

---

## 5. 文件边界与冲突

- 每个文件同一时间只允许**一个写 agent**。
- 共享文件（`README.md`、技能索引、导航、`sitemap.xml`、`llms.txt`、配置）→ 由**主对话**在所有 agent 完成后统一改。
- 并行任务的产出目录尽量不重叠；重叠时改为串行。
- 收口时统一跑一次校验（语法、链接、测试），不为每个 agent 单独跑全套。

## 6. 汇报模板

```
## 结果
- 子任务 1：<agent> → <产出路径>，验证：<命令/检查> → 通过
- 子任务 2：……

## 方案取舍
- 备选：<最初设想的另一条路径>；未选原因：<成本 / 风险 / 范围>
- 当前方案：<一句话理由>

## 未决 / 需人工
- <不可逆操作、需拍板的点、存疑事实>
```

## 7. 反例清单

| 反例 | 后果 | 正确做法 |
|---|---|---|
| 主对话自己 grep 全库再派活 | 上下文被灌满，编排失焦 | 交给 Explore，拿结论再派 |
| 多个 agent 同改一个文件 | 互相覆盖、改动丢失 | 文件边界隔离，冲突改串行 |
| 只信 agent 摘要 | 汇报与实际改动不符 | 读实际 diff / 文件 + 跑校验 |
| 指令只有窄步骤 | 前提错了仍机械执行 | 给背景、目标与已排除项 |
| 把任务拆成 10 个单文件 agent | 协调成本 > 收益 | 同模块合并，3–5 个子任务 |
| 研究任务不要来源 | 数字级事实不可用 | 要求 URL + 日期 + 原文摘录 |
| 主对话顺手做子任务 | 上下文爆、职责混乱 | 守住「只编排」 |
