# 编排模式（orchestrate-mode）

> **定位：元技能。** 它管「活怎么分、谁去干、怎么收」，不直接产出业务内容。
> **核心约束：主对话只编排** —— 拆解、派发、收口、汇报；实际执行交给 sub agent。
> 本文件是公开可复用版本：不依赖作者的工作区，可放进任意 `skills/` 库。
> 与 [skill-evolution](../skill-evolution/SKILL.md) 分工：那个整理**流程**，本技能**执行**流程。
> 规则优先级：用户指令 > 项目规则 > 本技能。

---

## 1. 触发 / 不触发

**触发（先加载本技能，再按 §3.0 分级）**

> **默认规则**：收到任何开发、重构、批量改造或资料研究任务，只要判定为**中等及以上复杂度**，就先加载本技能；简单小改动不必加载。

- **复杂度中等及以上（任一）**：≥3 个文件；跨模块 / 跨层（前端 + 后端 + 数据）；新增功能、重构、批量改造；需要多源检索 / 对比 / 事实核验；子任务可并行；预计 ≥10 轮工具调用或会灌满上下文。
- **确认 / 放行类**：「执行吧」「可以」「确认」「确认方案」「按方案做」「执行开发」「进行开发」「开始做」「动手吧」—— 表示允许开工，**不等于必须编排**。
- **用户点名**：「编排模式」「开编排」「拆给 sub agent」「主对话只编排」。

> **确认词只是「允许开工」，不是「必须编排」**。收到「可以 / 确认 / 执行吧」后仍要分级：L0 直接做、L1 派一个 agent、只有 L2 才进入编排模式。不要因为出现确认词就把小改动拆成多 agent。

**不触发（主对话直接做）**

- 单文件、≤30 行、无检索的小改动：改错字、调参数、加一行日志、改文案。
- 读一个文件就能答的单点问题。
- 路径已明确的机械联动（如只更新索引一行）。
- 拆解成本高于执行成本时 —— **不为编排而编排**。

> 判定口诀：**一个文件、一次改、不用查** → 直接做；否则编排。

## 2. 输入 / 输出

**输入**

- 目标与验收标准（可验证，不写「做好一点」）。
- 涉及目录 / 文件范围。
- 模式：`无人值守`（默认，少提问，自行判断）或 `互动模式`（关键分叉逐个确认）。
- 约束：只读 / 可写、是否对外发布、是否允许提交。
- 已有资料与已排除方案。

**输出**

- 编排计划：子任务、依赖关系、责任 agent。
- 每个 agent 的完整指令（见 §3.3）。
- 汇总结果 + 验证记录 + 未决项 + 方案取舍。

## 3. 主流程（6 步）

### 3.0 分级

按 [references/orchestration.md](./references/orchestration.md) §1 判 L0 / L1 / L2：

| 级别 | 做法 |
|---|---|
| **L0 直达** | 主对话自己改 + 自查，不派 agent |
| **L1 单兵** | 派 1 个 agent，主对话验收 |
| **L2 编排** | 拆 DAG + 多 agent 并行 / 串行 |

只有 **L2 才算「进入编排模式」**。

### 3.1 拆解

- 目标 → 可独立验收的子任务；每个写清：输入、产出、验收标准、文件边界。
- 画依赖：无依赖 → 并行；有依赖 → 串行；结构不明 → 先用 Explore 探路再拆。
- 子任务控制在 **3–5 个**；超过 8 个通常拆得太碎，合并回同模块。

### 3.2 选型

按 [references/orchestration.md](./references/orchestration.md) §2 路由表选 agent 类型：探索用 Explore（只读）、明确编码用 general-purpose、架构用 backend-architect、页面验收用 browser_use、计划用 Plan、模糊需求用 Orchestrator。

### 3.3 写指令

每份指令必须含七项：**背景（为什么做）/ 目标与验收 / 已知信息与已排除 / 文件边界 / 约束 / 产出格式 / 禁止事项**。模板见 references §3。

- 给足上下文，让 agent 能自行判断；不要只给窄步骤（前提错了，步骤就是废纸）。
- **不外包理解**：不写「根据你的发现去修」，而是写清改哪个文件、哪几行、改成什么。

### 3.4 派发

- 独立任务**同一批并行**发出；有依赖的等前序结果再派。
- 长任务用后台运行，主对话继续做不冲突的准备工作。
- **同一文件只派一个写 agent**；共享文件（README、技能索引、导航、sitemap、配置）由主对话统一改。
- 失败不重发同一指令：补信息、换 agent，或降级回 L0 自己做。

### 3.5 收口验证（trust but verify）

- 读**实际改动**，不只看 agent 摘要；核对文件存在性、引用可达性、语法 / 测试结果。
- 研究型任务抽查来源与日期；**数字级事实必须复核**后才可引用。
- 两个 agent 结论冲突 → 主对话裁决，或再派一个核验任务。

### 3.6 汇报

按「结果 + 未决」两段：① 做了什么 + 可验证结果；② 未决 / 风险 / 需人工确认。并附**备选路径与取舍理由**。只说结论与证据，不转述过程噪音。

## 4. 编排纪律（主对话）

- **不自己全库搜索**：探索交给 Explore，结论回来再用。
- **不重复 sub agent 的工作**：派出去就不再自己搜同一件事。
- **不做搬运工**：agent 已读完的文件不重复读，只读关键片段验收。
- **不同时给两个 agent 同一文件的写权限**。
- **不为编排而编排**：L0 的活直接做；拆解成本高于执行成本就停。
- **超范围即停**：任务超出原范围时按 §5 升级确认，不擅自扩大。

---

## 5. 分叉与升级

| 情况 | 动作 |
|---|---|
| 子任务互不依赖 | 并行派发 |
| 后一步依赖前一步产出 | 串行 |
| 结构不明 | 先 Explore，再决定拆法 |
| 不可逆（删除 / 覆盖 / 发布 / 改名） | **停**，交人工确认 |
| 影响面超出本次任务 | **停**，说明并确认 |
| 两种理解产出完全不同 | 互动模式逐个提问；无人值守自选一条并在汇报中标出 |

## 6. 坑与反例

- **只信摘要** → 摘要说的是意图，不是实际改动；必须验证。
- **多 agent 抢同一文件** → 互相覆盖；用文件边界隔离。
- **指令太窄** → agent 机械执行，遇分支即错；给背景与目标。
- **拆太碎** → 协调成本 > 收益；同模块合并给一个 agent。
- **研究不核来源** → 数字级事实不可对外；要求 URL + 日期 + 原文摘录。
- **主对话顺手做子任务** → 上下文爆掉、编排失焦；守住「只编排」。

- [ ] 汇报含结果、验证、未决项、备选方案取舍
