# 一条语音指令，如何让 Agent 写出一份可复用的经验总结

## 一、给人类：三句话说清

这条语音指令产出了一份 13 节的 [DSH 插件检索经验总结](../../critiques/agent-framework/2026-10-dsh-plugin-search-experience.md)：把一次真实的插件检索、安装和踩坑过程，整理成下一个 Agent 能照着做的文档。能写成这样，关键不是措辞，而是先倒出一手事实：装了什么、哪里坏了、什么装不上、什么没需求。再告诉 Agent 读者是谁、必须有哪些章节；发布前复核数字与版本，避免把推测写成实测。

### 人类版模板（语音直接说）

1. 帮我整理一份经验文档，开头先用 1~3 句话说清重点。
2. 本次任务我的反馈是:***。
3. 读者主要是 Agent，总结本次任务的流程和经验。

## 二、给 Agent：完整版

### 1. 五个有效动作

| 动作 | 做法 | 为什么有效 |
|---|---|---|
| 先定读者 | 明确「这个产出主要是给 Agent 阅读的」 | 决定了写法是表格、清单、硬约束和 SOP，而不是面向人类的散文 |
| 先给事实 | 列出装了哪些、哪些有 bug、哪些装不上、哪些没需求 | Agent 不用猜，也不会把「看起来有用」写成「实际可用」 |
| 指定骨架 | 顶部先列已装插件与用途；加入第一轮产出；加入 HTML 勾选与复制设计 | 关键内容不会被写成一篇泛泛的「心得体会」 |
| 给参照物 | 给出两份旧交付物的本地路径 | Agent 能对齐术语、结构和实现细节，不必从零发明 |
| 记录协作事实 | 写明 hy4 / step5 / DeepSeek V4.1 各做了什么、为什么拆分 | 文档可追溯，也避免把多模型协作包装成单一模型的「全能叙事」 |

这五条里，真正稀缺的是第二条。检索方法、章节结构、文风，Agent 都能补；**只有你亲测过的失败、报错和「没需求」，它补不出来。**

### 2. 为什么语音输入反而有效

语音输入不擅长结构，但擅长把刚发生的事实倒出来：插件名、报错、版本号、谁做了什么、哪些已经放弃。

这恰好是 Agent 最缺的输入。结构是它的强项，事实是你的强项。要求一个人对着输入框一次性写出「结构完整、事实准确」的长指令，反而容易卡住。

代价是转写噪音。整理时只修标点、分段和明显的转写错误，插件名、版本号、状态不改。**口述给事实，文档给结构。**

### 3. 整理后的指令

> 以下为整理版：分段、标点、明显转写错误有修正，并按分享需要做了精简；事实未改。

```text
整理一下经验文档，中文命名写入到工作目录。

例如：你是如何搜索插件的，都遇到什么问题，有什么经验心得；包括我提供的信息，哪些是可以使用的；你都从哪里搜集 DSH 插件和技能。

我安装的是：
- dsh-chat-toc：有一些 bug，会在不该显示的地方出现，没有标出搜索到的位置
- dsh-notify-me：还没测试
- dsh-todo-board：看似不错，还没测试

其他插件大多数无法安装、不适配当前版本，或者不符合需求：
- 生成式 UI：无法安装，dsh-visualize@0.2.1 与 DSH 0.2.1-rc.2 不兼容
- 缓存续存时长：没需求
- 快速撤回 Mongfayi/dsh-recall：没需求
- ne-ilyxa/dsh-session-drafts：找不到相关插件

文档顶部应该先写上：已安装的插件有哪些，用处分别是什么。

参考：
- G:\trae\work\DSH汇报\交给DSH的插件与技能安装指南.md
- G:\trae\work\DSH汇报\DSH插件与技能分类汇报.html

经验总结再加入：最开始第一轮工作的产出，以及制作这个 HTML「可勾选、支持复制到剪贴板」的思路和经验。

查看下面这份经验总结是否有什么遗漏；如果有，可以继续补充。这份经验总结是另一个 Agent 参考你的产出编写的。你有什么可迁移的心得，也写入里面，对其他 Agent 有用的就写。这个产出主要是给 Agent 阅读的。

并记录：之前插件查找的工作是 hy4 完成的，汇报页面是 step5 完成的，经验总结是 DeepSeek V4.1 制作的。使用多个模型是因为 Step 5 本来是测试能力，但现在太拥堵了、速度慢。

文档如下：
G:/trae/work/reports/DSH插件检索经验总结.md
```

### 4. Agent 版可复用模板

```text
你是经验文档编辑。请把我下面的一次性经历，整理成一份可复用的经验文档。

读者：Agent（下一个要执行同类任务的人）。
目标：让读者能按文档复现关键步骤，而不是读一篇感想。

我提供的一手事实：
- 已安装 / 已使用：
- 实测问题：
- 失败或放弃：
- 明确没需求的：

文档必须包含（按此顺序）：
1. 顶部：已安装清单 + 各自用途
2. 信息来源与检索方法（可复用步骤）
3. 踩过的坑：现象 → 原因 → 证据 → 规避方法
4. 装前检查清单（SOP）
5. 第一轮产出 / 过程稿：<路径>
6. 协作分工：谁做了什么、为什么这样分
7. 版本 / 时间基线：本文结论基于 <版本>，<日期> 后需复核

写作要求：
- 中文命名，写入工作目录
- 开头先给 1~3 句话总结
- 事实、推断、建议分开标注
- 数字级事实标注「检索当日快照，待复核」
- 不编造未提供的实测结论

参考资料：
- <路径 / 链接>
```

两个使用要点：

1. **先给事实，再让它组织。** 事实越具体，成文越不需要「编」。
2. **一次只让它做一件事。** 先补漏、再成文、最后审数字；混在一轮里，容易得到一份看起来很全但无法核对的稿子。

### 5. 这条指令没做到、下次要补的

- **数字级事实没有先标「待复核」。** star 数、条目数、版本区间都应写成「检索当日快照」，发布前再核一遍。
- **没有区分事实、推断和建议。** 下次可以直接要求 Agent 用三种标记，避免把推测写成实测。
- **没有给验收标准。** 比如「读者能否在 10 分钟内复现关键步骤」，比「写得完整一点」可执行。
- **没有先定公开边界。** 应该在指令开头写清 `visibility`，以及哪些路径、姓名、内部信息不能进文档。

### 6. 一句话收尾

**把 AI 当编辑，不要当证人；证人是你自己。**
