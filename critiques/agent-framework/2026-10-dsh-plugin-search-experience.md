## 一、先记住四个硬事实

这四条决定了整个检索策略。不先接受它们，后面的活基本白干。**顺序就是优先级：先判断要不要装，再判断装不装得上。**

**1. 官方内置优先，插件只补差。**
先查官方 CHANGELOG 和内置能力，再去找插件。DSH 迭代很快，很多"插件需求"一两个版本前已经被官方做掉了：Turn Rail 从 **0.1.2 起官方自带**，`vlln/dsh-navbar` 因此归档（坑 3）；文字草稿官方本来就用 localStorage 存，会丢的只是附件和"新会话复用吞草稿"（7.3）。反过来做，轻则重复造轮子，重则两个东西抢同一块 UI，出了 bug 还查不出是谁的。

**2. 版本门比功能重要。**
DSH 目前**每一条发布线都是 prerelease**，1.7~2.8 天一个版本，且带破坏性变更。插件能不能装，取决于它的 peer 约束落在哪个区间，而不是它功能多好。清单上写着「支持 DSH」没有意义，得看 `peerDependencies` 和 README 里的兼容表。

**3. npm 上同名包泛滥，scope 是唯一标识。**
这是本次最大的发现，也是老大装错包的直接原因（详见第六节坑 1）。`dsh-visualize`、`dsh-sound`、`dsh-recall` 这几个无 scope 名字，底下全是**别人的包或占位包**。安装命令里少了 `@scope/`，装到的就是完全不相干的东西。

**4. 目录描述 ≠ 实际功能，必须读 README。**
`awesome-dsh-plugin` 是人工审核过的，相对靠谱；但 deepseek1024 那 13807 条是自动抓的 GitHub description，**和实际功能经常对不上**。而且清单有滞后：`vlln/dsh-navbar`（★51）早就归档了，还挂在列表里。

## 二、第一轮工作的产出（2026-10-13）

第一轮和这次是两种完全不同的活，产出形态也不同。放在一起对照，才看得出长进在哪。

### 2.1 两份交付物：一份给人看，一份给 agent 执行

都在 `G:/trae/work/DSH汇报/`：

| 文件 | 体量 | 面向 | 用途 |
|---|---|---|---|
| `DSH插件与技能分类汇报.html` | 34KB / 822 行 | **人** | 分类浏览 → 勾选 → 一键复制清单 |
| `交给DSH的插件与技能安装指南.md` | 7.5KB / 150 行 | **agent** | 整体粘贴给 DSH，让它自己装完并汇报 |

**关键认知：第二份不是文档，是指令。** 开头第一句就是：

> 用途：把本文档**整体粘贴给 DSH**（作为一条指令），DSH 按本文档自主完成「环境预检 → 逐个安装 → 验证 → 汇报」。

当时那台机器没装 DSH（和现在不一样），所以任务不是「我帮你装」，而是「写一份能让 DSH 自己装的说明书」。这个定位决定了整份文档的写法——**不是在陈述事实，而是在约束行为**。

### 2.2 安装指南的骨架（可直接复用）

1. **给执行方的总体指令** —— 5 条硬约束：
   - 不跳步静默继续（任何一步失败，记错误和日志，继续下一项，最后统一汇报）
   - 安装命令以权威来源为准，**不许凭记忆拼接**
   - 先插件后技能（部分技能依赖插件运行时）
   - 每装一项验证一项，不要全部装完再统一验证
   - 可回退：先「禁用」定位，确认无效再「卸载」，不直接删文件
2. **环境预检表** —— `dsh --version` / Node 版本比对 / 网络可达 / 备份配置目录
3. **权威来源优先级** —— dsh-market → awesome 清单 → GitHub README；**三者冲突时以 README 为准**，并在汇报里注明分歧
4. **选型清单** —— 8 项，每项带分类 / 作者 / 用途
5. **分批安装顺序** —— 基础设施 → 效率工具 → 能力扩展 → 技能包
6. **逐项验收方法** —— 每装完一项当场怎么验
7. **验收总标准** —— 全部完成后过一遍
8. **故障处理预案** —— 4 种现象对应处理
9. **要求执行方输出结构化交付物** ← 这条价值最高

第 9 条规定了输出格式：安装结果表（名称 / 成功失败 / **实际执行的命令** / 安装后版本号）+ 失败项（报错摘要 + 已尝试处理 + 建议下一步）+ 验证记录 + 最终状态 + 备份位置。

**为什么它重要：** 它预判了「agent 装完只会说都装好了」这个默认行为。不提前规定格式，拿回来的就是一堆没法核对的话术。

### 2.3 对照：第一轮选的，和最终装上的，零重叠

| | 清单 |
|---|---|
| 第一轮选的（8 项） | dsh-web-ui、dsh-better-sidebar、dsh-at-file、ModLens、dsh-agent-teams、dsh-context-doctor、dsh-plugin-dev-skills、dsh-skill-import |
| 最终装上的（3 项） | dsh-chat-toc、dsh-notify-me、dsh-todo-board |

**一个都没重叠。** 原因不止一个，拆开看：

- 第一轮按「市场分类 + 评分」选，天然倾向**全家桶**（`dsh-web-ui` 一次带看板 + Git 图谱 + Token 统计），结果是一堆功能互相重叠的东西
- 第二轮按**具体痛点**选（「任务完成要有声音」「任务1完了自动开新对话干任务2」），逐个读 README 核实，才筛出真对口的
- 第一轮那 8 项里，**没有一项是冲着对话导航、通知、队列这些后来才暴露的痛点去的**——因为当时还没有这些需求
- **还有一层原因容易被漏掉：那 8 项本身没被核实过。** 它们来自一篇社区汇总（二手资料），没查 npm 是否存在、peer 是否覆盖、Windows 是否兼容。也就是说，除了"选错方向"，还有一部分是"根本装不上"

**两条教训，别混成一条：**

1. **选型要有需求驱动。** 没有痛点支撑的选型，选出来都是「看起来有用」的东西，命中率低一个量级。
2. **二手清单不能直接当输入。** 从博客/汇总里抄来的候选，必须先过一遍核实（字段表见第十节）——否则页面做得再漂亮，也只是把别人的未经验证当成了事实。

## 三、HTML 的「可勾选 + 一键复制」是怎么做的

这份页面是整套流程里最值得复用的部分，单独拆开讲。

### 3.1 先明确它要解决什么

老大不想「看报告 → 自己记 → 再打一遍」，要的是：**勾完 → 复制 → 直接粘回对话**。

所以它不是给人「读」的报告，而是一个**选择器 + 文本生成器**。这个定位决定了后面所有技术选择。

### 3.2 数据结构：三层树，叶子是唯一可选项

```js
DATA.branches = [
  { id:"plugins", name:"插件", children:[
      { id:"ui", name:"交互与 UI 增强", children:[
          { id:"dsh-web", name:"dsh-web-ui", author:"...", desc:"...", link:"..." }
      ]}
  ]}
]
```

递归渲染出 checkbox，叶子带 `data-lid`、分类带 `data-gid`，上层的全选/半选和事件委托都靠这两个属性定位。

### 3.3 三态勾选：`indeterminate` 是关键

叶子 → 分类 → 分支，父级必须三态：

```js
cb2.checked       = n2 === total && total > 0;
cb2.indeterminate = n2 > 0 && n2 < total;   // ← 少了这行，分不清「选了部分」和「全没选」
```

没有 `indeterminate`，父级只能全选/全不选，用户看不出自己到底选了多少。

### 3.4 单一状态源，别往 DOM 上存状态

只维护一个对象：

```js
var selected = { leafId: true };   // 唯一真相
```

任何点击都走 `setLeaf(id, val)` → 统一 `refresh()`，由它重算父级三态、顶部计数、侧栏已选清单。

**反面做法**是在 checkbox 的 DOM 属性上分散读写状态——改一处要同步三处，必然对不上。

### 3.5 生成复制文本：两个让清单「能用」的细节

`buildCopyText()` 按 `■ 分支（已选 N 项）` → `序号. 名称` → `分类｜作者` → `说明` → `链接` 排列。两个细节把它从「复制一堆名字」变成「可执行清单」：

1. **开头带时间戳和来源** —— `生成时间：2026-10-13 17:28（来源：DSH 分类汇报页）`，贴回去能追溯是哪一版
2. **结尾加一句指令钩子** ——
   ```
   —— 请依据以上选择，重新整理插件与 Skills 清单 ——
   ```
   让粘贴的文本**自带意图**。否则还得补一句「帮我整理一下」，而那句往往会被漏掉。

### 3.6 复制必须做三层降级（这是踩过的坑）

```js
function copyText(text){
  if (navigator.clipboard && navigator.clipboard.writeText){
    navigator.clipboard.writeText(text).then(ok).catch(fallback);
  } else { fallback(); }
}
function fallback(){                 // 第二层：隐藏 textarea + execCommand
  ta.value = text; ta.focus(); ta.select();
  try { document.execCommand("copy"); }
  catch(e){ openModal(text); }       // 第三层：弹窗让人手动 Ctrl+C
}
```

**为什么必须降级：** `navigator.clipboard` 要求 **secure context**（https 或 localhost）。这份 HTML 是双击用 `file://` 打开的，部分浏览器里直接调会 reject。只写第一层，用户点了没反应，还不知道为什么。

**第三层弹窗**用 `<textarea readonly>`（防误改）+「全选」按钮（省得手动拖选）+「复制」按钮。全选按钮顺带解决了手机上长按选文本很麻烦的问题。

### 3.7 反馈与自包含

- **toast**：2.6 秒自动消失，失败用红色区分。复制这类操作如果没有反馈，用户会怀疑没点上、连点好几次
- **单个 HTML，零外部依赖**：无 CDN、无字体文件、无框架。双击就能开，不用起服务器，发给别人也不掉样式

### 3.8 这次没做好、下次要改的

1. **没有 localStorage** —— 勾选状态刷新就丢。加三行就够：`selected` 变化时 `localStorage.setItem`，初始化时读回
2. **树形布局在手机上不可用** —— 左侧分类树 + 右侧已选清单，窄屏直接挤爆。这页是 10-13 做的，老大也是 10-13 才提出「要能用手机看」。**下次这类页面先做单列，再用 `@media (min-width:700px)` 开双列**
3. **勾选粒度只到叶子** —— 想「整个分类全要」得一个个点。三态 checkbox 有了，但缺一个「点分类秒全选」的快捷操作

## 四、我实际是怎么检索的

### 4.1 信息来源按权威度排序

| 层级 | 来源 | 规模 | 可信度 | 用途 |
|---|---|---|---|---|
| ① 元信息 | `Electricitysheep/dsh-handbook` 第 15 章 | 1804 插件仓库盘点 × 780 帖讨论区 | 最高（交叉验证过） | **先看这个再动手**，能提前避开整类坑 |
| ② 精选清单 | `awesome-dsh-plugin/awesome-dsh-plugin` | 5786 条目 | 高（人工审 PR，逐条核对源码） | 主力检索对象 |
| ③ 全量目录 | `imsai-sh/awesome-deepseek-harness-plugins` | 13807 插件 | 中（自动抓取） | 补漏，配公开 API |
| ④ 成品市场 | `dsh-market/dsh-market`（★7164） | 同上 | 中 | 直接点装，但看不到细节 |
| ⑤ 技能侧 | `cxy9204/dsh-skill-store`、`yzfly/awesome-dsh-skills` | 14 万+ / 1091 | 高 | 找 skill 而非 plugin 时用 |
| ⑥ 开发侧 | `PerryLink/dsh-plugin-guide` | — | 高 | 自己想改/写插件时用 |

**最有价值的是 ①，但上一轮我几乎没用上。** dsh-handbook 第 15 章那句话直接解释了老大「大多数插件无法安装」的原因：

> 🪟 **Windows 是第一痛点** —— 中文路径（15+ 帖同根因）/ koffi / 端口 / 子进程

在 win32 上装 dsh 插件，失败率高不是运气问题，是**结构性问题**。下次应该在检索阶段就把「Windows 兼容性」当筛选条件，而不是装完再踩。

### 4.2 四步法（可复用）

```
第一步：拉全量清单到本地
        ↓
第二步：本地 grep 关键词，出候选（零配额消耗）
        ↓
第三步：逐个抓 README 核实（raw.githubusercontent 不消耗 API 配额）
        ↓
第四步：npm registry 查真实包名 + peer 约束
```

**第一步：拉清单**

```bash
curl -sL -o awesome-zh.md \
  https://raw.githubusercontent.com/awesome-dsh-plugin/awesome-dsh-plugin/main/README.zh.md
# 中文版 1.76MB，英文版 1.86MB
```

清单结构很规整，好解析：`### 分类名` 开头，下面每行 `- [owner/repo](url) — 描述`。所以本地解析只要十几行 Python：

```python
txt = open('awesome-zh.md', encoding='utf-8').read().split('\n')
cats, cur = {}, None
for ln in txt:
    if ln.startswith('### '):
        cur = ln[4:].strip(); cats[cur] = []
    elif cur and ln.startswith('- ['):
        cats[cur].append(ln)
allitems = [(c, i) for c, v in cats.items() for i in v]   # 5786 条
```

然后按需求分组打关键词。**关键：中英双搜。** 中文清单里"缓存""压缩""撤回"能搜到，但"cache""compaction""rewind"才能捞到那些描述写英文的插件。同一批候选要跑两遍。

**第三步：核实 README**

```python
for br in ('main', 'master'):     # 分支名不统一，两个都试
    url = f'https://raw.githubusercontent.com/{repo}/{br}/README.md'
```

这一步是**唯一能防住"描述骗人"的环节**。本次至少三次靠它纠正了判断：

- `songoao25/dsh-auto-compact` —— 清单里有，README 抓不到，仓库实际已不可用
- `vlln/dsh-navbar` —— README 第一行就是 `ARCHIVED (read-only)`，官方内置后归档
- `linhx1999/dsh-writing-pad` —— 描述像"草稿保存"，读了才发现写着「草稿暂存在 Host 内存中」，**重启即丢**，跟需求正好相反

**第四步：查 npm 真实身份**（本次教训新增，务必做）

```bash
curl -s "https://registry.npmjs.org/@nagi-ovo%2Fdsh-visualize" | \
  python -c "import sys,json;d=json.load(sys.stdin);print(d['dist-tags'], list(d['versions']))"
```

看三件事：`dist-tags.latest`、版本列表、`peerDependencies['@deepseek-ai/dsh']`。

### 4.3 几个具体操作细节

**没有 `gh` CLI 也不影响。** 本机没装，但 GitHub API 匿名可用：
- core 60 次/时，search 10 次/分 —— 够用但别浪费
- `raw.githubusercontent.com` **完全不消耗 API 配额**，抓 README 优先走它
- 批量抓用线程池，12 个并发，20 个仓库十几秒完

**deepseek1024 的公开 API 好用但会限流：**

```
https://api.deepseek1024.com/v1/plugins/search?q=<关键词>&limit=25
```

返回 429 `RATE_LIMITED` 很快。**拿到结果立刻落盘 JSON，不要重试**（我第二次全量请求被限，靠第一次的落盘文件才救回来）。

**中文关键词在 API 里效果不如本地 grep。** API 走的是关键词匹配，中英文混搜容易漏；本地全量清单 grep 更可控。

## 六、这次踩的坑（按损失排序）

### 坑 1：npm 同名包劫持 —— 损失最大

这是老大装不上/装了不对的直接原因。实测三例：

| 无 scope 名 | 实际是什么 | 我要的那个 |

| `dsh-visualize@0.2.1` | 作者 **brzvsk**，`visualize_html` 工具，另一个插件 | `@nagi-ovo/dsh-visualize`（★309，**latest 只到 0.1.7**） |

### 坑 2：README 声明的兼容区间不可信

`dsh-visualize` README 写「兼容 DSH 0.1.1-rc.2 到 0.2.1-rc.2」，但实际在那个区间边缘会炸。**作者写的兼容表是自测结论，不是契约**——DSH 边发版边改协议，README 更新往往滞后。

真正可靠的只有 `package.json` 里的 `peerDependencies`，而且**只有主动声明了才拦得住**。对比一下：

- `dsh-todo-board@0.13.4` → `peer: >=0.1.7-rc.2` ✅ 装错版本**安装时**就失败
- `dsh-context@0.74.0` → `peer: >=0.1.7-rc.2 || >=0.2.0-rc.2` ✅
- `@nagi-ovo/dsh-visualize`、`dsh-chat-toc`、`dsh-notify-me` → **完全没声明** ❌ 装错版本一路畅通，运行时才炸

`dsh-todo-board` 的 README 里有一段讲得很透，值得记住：

> `engines.dsh` 是一扇**哑门**：npm 只校验它认识的引擎名（`node` / `npm`），自定义引擎名不参与检查 —— 装在旧版上**不会有** `EBADENGINE` 警告。它只是一个**声明**，从来不是门。

所以看到 README 写 `engines.dsh` 不要当回事，**要看 `peerDependencies['@deepseek-ai/dsh']`**。

### 坑 3：清单有滞后，归档插件还在列表里

`vlln/dsh-navbar`（★51）在精选库里正常挂着，README 第一行是：

> **ARCHIVED (read-only)** — The official DSH web shell shipped a built-in Turn navigation rail in the **0.1.2 series**

顺带一个有用的信息：**官方从 0.1.2 起就内置了 Turn Rail 导航轨**（悬停预览 / 点击跳转 / 阅读位置跟踪）。所以对话导航类插件都是在官方轨道上做增强，不是从零提供。这直接影响选型判断。

### 坑 4：找不到 ≠ 没有

老大说 `ne-ilyxa/dsh-session-drafts` 找不到。实际情况：**它在 npm 上有 0.7.0**，只是：
1. 无 scope 名 404
2. 可能没进市场索引（市场只收 `dsh.bundle` 声明 + 已知版本号的）
3. 作者 README 说「published **manually** by the maintainer」，CI 不碰 registry，所以收录延迟大

**不是不存在，是搜不到。** 这种情况只能按 README 给的确切包名装。

### 坑 5：Windows 是结构性痛点，不是个别插件的问题

来自 dsh-handbook 第 15 章的盘点（1804 个插件仓库 + 780 帖讨论区交叉验证）：

> 中文路径（15+ 帖同根因）/ koffi / 端口 / 子进程

老大在 win32 上，**「大多数插件无法安装或不兼容」很可能是这个共同根因**，而不是每个插件各有各的问题。排查顺序建议：

1. 工作目录路径有没有中文/空格（`G:\trae\work` 没中文，但插件缓存目录可能在 `C:\Users\muamu\` 下，`muamu` 是英文，OK）
2. `pnpm` 的 `allowBuilds` 有没有挡住 `prepare` 脚本（很多插件从 git 装需要它）
3. 端口 3080 是否被占用
4. Node 版本 —— 大量插件要求 `22.19+` 或 `24.x`，本机是 22.22.2 ✅

### 坑 6：会话格式 v4 是硬门槛

`dsh-todo-board` 的 README 提了一句很关键的：

> 插件注入的每条消息都带一个**生产者自有的 source**（`{ kind: 'plugin:dsh-todo-board', form: 'notice' }`）：这是 v4 的硬性要求，旧 v3 的写法会被持久化层拒绝，而**拒绝会带走整个回合**——不只是那条提示。

意思是：老插件用 v3 写法往会话里注入消息，在 v4 会话格式下会**连带整个回合一起失败**。这类插件不是"功能不全"，是"会把会话搞坏"。装之前值得看一眼作者有没有适配 0.2.x。

### 7.1 `dsh-chat-toc` 的两个 bug

老大报的两条，我看了下都能对上它的实现方式：

**「会在不该显示的地方出现」** —— 它的右上角工具条是"内嵌于右上角操作区（紧邻 Session log 按钮）"。这种靠 DOM 位置挂载的插件，一旦宿主页面结构变了（比如切到设置页、插件页、轨迹视图），挂载点还在但语义已经不对，就会在不该出现的页面上冒出来。

**「没有标出搜索到的位置」** —— 它的搜索是「点开搜索框，输入即时模糊高亮当前页匹配；长对话按 Enter 触发全会话深度搜索」。如果只输关键词没按 Enter，或者命中在**未加载的历史窗口**里，就不会有高亮和定位——因为它默认只处理已渲染的 DOM，全面模式才主动加载全历史。这算「功能没做到位」，不是纯粹 bug。

**建议：**
- 先去仓库提 issue（作者维护挺勤，31 个版本）。提的时候带上 DSH 版本号 + 复现页面
- 短期替代（**均未实测**，仅从 README 判断，装之前按第八节 SOP 再核一遍）：`liliuCourier/dsh-chat-outline`（左侧常驻大纲，按轮次列提问+最后回复，点击跳转，关键词过滤，蓝框标记当前阅读位置）或 `delaydai/dsh-jumpbar`（右缘 minimap，悬停预览、点击滚顶并高亮）
- 这两个的问题正好互补：chat-outline 有明确的"当前阅读位置"标记，jumpbar 的定位更精准

### 7.2 `dsh-visualize` 的正确装法

```sh
# 正确（带 scope）
dsh plugin --profile web add @nagi-ovo/dsh-visualize

# 如果想先看版本
npm view @nagi-ovo/dsh-visualize versions
# → 0.1.2 0.1.3 0.1.4 0.1.5 0.1.6 0.1.7   ← 没有 0.2.1

# 保险起见从 GitHub 装（跳过 npm 的版本混淆）
```

### 7.3 `dsh-session-drafts` 的正确装法


npm 上确认存在（0.7.0，2026-10-04 发布）。如果市场里搜不到就用这条命令直装。装完**必须重启 dsh web**（它不是热加载）。

## 八、下次的行动清单（SOP）

装任何一个 DSH 插件前，按这个顺序过一遍：

**⓪ 先查官方有没有**
- 翻一遍 CHANGELOG / 内置能力说明，确认要补的功能官方没做
- 典型已被内置的：Turn Rail（0.1.2+）、文字草稿持久化（localStorage）
- 判断标准：如果插件的全部价值就是"补一个官方已有小功能"，大概率不用装

**① 确认自己当前版本**
```sh
dsh --version
```
所有兼容判断都基于这个，别凭记忆。

**② 查 npm 真实身份（防同名劫持）**
```sh
npm view <包名> versions peerDependencies maintainers
```
- 版本号对不对得上 README 说的
- 有没有 `peerDependencies['@deepseek-ai/dsh']`，约束是否覆盖我的版本
- maintainers 是不是那个作者（防止装到 fork 或占位包）

**③ 抓 README 首屏看三件事**
- 第一行有没有 `ARCHIVED` / `DEPRECATED`
- 兼容表写的区间
- 安装命令是**带 scope 的包名**、`github:owner/repo`、还是 `<仓库路径>`（后者说明没发 npm）

**④ 看一眼它的实现方式，判断会不会跟别的插件打架**
- 接管 compaction 的 → 全机器只能装一个
- 接管右缘轨道 / 输入框 dock 的 → 同类只能装一个
- 靠 DOM 挂载的（chat-toc 这种）→ 宿主一升级就可能错位

**⑤ Windows 专属检查**
- 路径有没有中文/空格
- `pnpm` 的 `allowBuilds` 有没有拦 `prepare`
- 端口 3080 占用

**⑥ 装完立刻验证（profile 必须与安装时一致）**
```sh
dsh plugin --profile web add <包名>    # 装的时候带 --profile
dsh --profile web --dump-config        # 验的时候必须带同一个
```
装进另一个 profile 是最常见的"假成功"：配置里确实有，但你在用的那个没有。**装上了 ≠ 生效了。** 然后重启 `dsh web` + 刷新页面（很多插件不做热加载，README 里会写）。

## 十、补充：复盘时发现漏掉的五条

写完前九节又倒回去看第一轮的产出，有五条当时没写、但对下次有直接影响。前两条是流程缺口，后三条是执行细节。（原本还有一条「官方内置优先」，已经提升为第一节的第 1 个硬事实，这里不再重复。）

### 10.1 候选清单必须带"核实状态"列

第一轮那份 8 项清单只有 `名称 / 分类 / 作者 / 用途`，**没有一个字段能回答"它现在还能不能装"**。第二轮的零重叠，功能不匹配只是一半原因，另一半是那 8 项里有相当一部分在 npm 上根本对不上号（第一轮清单来自一篇社区汇总，没有做过 registry 核实）。

最小字段集：

| 字段 | 取值 | 怎么填 |
|---|---|---|
| 来源 | 博客汇总 / awesome / README / registry | 二级来源标「未核实」 |
| npm 是否存在 | 是 / 否 / 无 scope 名 404 | `npm view` |
| peer 是否覆盖当前版本 | 是 / 否 / **未声明** | `peerDependencies['@deepseek-ai/dsh']` |
| Windows 已知问题 | 有 / 无 / 未知 | dsh-handbook 第 15 章 |
| 核实时间 | YYYY-MM-DD | 清单会过期，时间就是保质期 |

没有这一列，清单只是一份"听起来都挺好"的愿望单。

### 10.2 淘汰清单是被浪费掉的资产

本次淘汰了 20+ 个候选，理由散落在对话里，**没有落成文件**。下次换个人、或者换个模型来做，会把同一批再调研一遍。

建议固定一个 `rejected.md`，一行一条：

```
候选 → 淘汰原因 → 证据（README 原文 / 报错 / issue 链接）→ 日期
```

它和"已装清单"同等重要：**已装清单省安装时间，淘汰清单省调研时间。** 而且淘汰理由是唯一能证明"这份清单被认真筛过"的东西。

### 10.3 装第三方插件前的最小安全审计

插件是跑在本机的 npm 包，`github:` 直装还会执行 `prepare` 脚本——等于在本机执行任意代码。最小四条（通用做法，本次未逐条执行）：

1. `maintainers` 是不是那个作者（防 fork、防占位包）
2. `scripts.prepare` / `postinstall` 有没有可疑命令
3. 最近发布时间与下载量（prerelease 生态里，长期不更新基本等于不可用）
4. 优先 npm 已发布版本，`github:` 直装只作退路

### 10.4 profile 一致性：装上了 ≠ 生效了

命令里带 `--profile web`，验证时也必须带同一个：

```sh
dsh plugin --profile web add <包名>
dsh --profile web --dump-config     # 必须能看到它
```

多 profile 环境里最常见的"假成功"，就是装进了另一个 profile——配置里确实有，但你在用的那个没有。

### 10.5 冲突要按"独占资源"分类，不是按插件名

第八节 ④ 提了"接管 compaction 的只能装一个"，可以再具体一层。下面这张表是从各插件 README 描述推断的，未实测冲突：

| 独占资源 | 典型插件 | 判断方法 |
|---|---|---|
| compaction / 上下文压缩引擎 | dsh-context、dsh-context-doctor 类 | README 出现 "hook into compaction" |
| 右缘轨道 / minimap | dsh-jumpbar、dsh-chat-outline | 都挂右缘，二选一 |
| 输入框 dock / 工具条 | dsh-at-file、slash 类 | 抢同一块输入区 |
| 通知通道 | dsh-notify-me 类 | 系统通知 + 声音只能有一个主控 |
| DOM 挂载点 | chat-toc（右上角操作区） | 宿主改版即错位 |

装之前直接问作者一句"是否接管 X"，比装完打架再排查便宜得多。

## 十一、多模型协作记录

这份文档不是一次对话的产物，三个环节由三个不同的模型完成：

| 环节 | 执行方 | 产出 |
|---|---|---|
| 插件检索、核实、安装踩坑 | **hy4** | `dsh_search/` 下的脚本与缓存、候选清单、第六节坑 1–6、第七节实测归因 |
| 汇报页面（勾选 + 复制） | **step5** | `DSH汇报/DSH插件与技能分类汇报.html`（34KB / 822 行），第三节拆解的实现 |
| 经验总结（本文） | **DeepSeek V4.1** | 本文档 |

**为什么拆：** Step 5 原本的定位是"测试能力"的模型，现在排队拥堵、速度慢。把重活按性质分给不同模型，是当时最现实的选择——不是架构设计，是被排队逼出来的。

**这套拆法能成立的原因（对其他 agent 有用）：**

1. **交接物是文件，不是上下文。** 三段之间只传文件：候选清单 → HTML → 总结 MD。任何一个模型都不需要知道另一个模型的对话历史。
2. **每个模型只做自己那类活。** 检索要"大量工具调用 + 耐心核对"；页面要"一次生成大量结构化代码"；总结要"读多份材料 + 归纳冲突"。混在一个模型里做，容易被上下文长度和工具轮次拖死。
3. **代价是交接损耗。** 所以交接文件必须自解释：用途、输入、输出格式、失败怎么办。`交给DSH的插件与技能安装指南.md` 是标准样本——不依赖任何对话上下文，换谁来执行都行。
4. **风险是事实漂移。** 不同模型对同一件事的判断会不一致（第一轮清单说"可用"，第二轮实测说"装不上"）。处理原则：**以实测为准，冲突记录不删**。这也是第七节要单独成章的原因。

一句话：**多模型协作的瓶颈不在模型能力，在交接物的自解释程度。**

## 十二、汇报与交付心得（给其他 Agent）

第三节讲的是"怎么实现"，这里讲"怎么让交付物真的被用起来"。都是从这次的实际结果倒推出来的。

### 12.1 先定角色，再动手

同一个需求，"做个汇报"可能是三种完全不同的东西：

| 角色 | 用户拿到后的下一个动作 | 写法 |
|---|---|---|
| 报告 | 读、点头、存档 | 结论先行，论据在后 |
| 选择器 | 勾选、复制、粘回对话 | 树形 + 三态 + 一键复制 |
| 指令 | 整段丢给另一个 agent 执行 | 硬约束 + 验收标准 + 输出格式 |

**判断方法就一句：用户拿到之后的下一个动作是什么？** 这次第一轮判断对了，出了两份（选择器 + 指令），所以形成了闭环：勾选 → 复制 → 粘贴 → 生成安装指令 → 执行。

### 12.2 分类维度决定命中率

第一轮按"交互与 UI / 能力与架构"分，是**厂商视角**：逛着舒服，选着没用。第二轮按"任务完成要有声音 / 任务 1 完了自动开任务 2"选，是**痛点视角**：命中率高一个量级。

给用户的选型页，至少要让每个条目能回答"**解决我什么麻烦**"。只有功能描述的清单，用户只能凭感觉勾——这也是"看起来有用"清单泛滥的原因。

### 12.3 让粘贴回来的文本自带意图

两个小设计，成本极低：

- 开头：`生成时间 + 来源`，可追溯是哪一版
- 结尾：`—— 请依据以上选择，重新整理插件与 Skills 清单 ——`

没有结尾这句，用户粘回来还得补一句"帮我整理"，而那句经常被漏掉，或者在多轮里被冲掉。

### 12.4 数据来源必须标在页面上

这是第一轮最该改、当时没意识到的一点：那 8 项来自一篇社区汇总（二手资料），页面上却和"作者、用途"并列展示，看起来像核实过的事实。下游 agent（包括写这份总结的我）直接拿它当输入，生成了一份看起来很专业的安装指南。

**规则：二手资料在页面上必须明示「来源 + 是否核实 + 核实时间」。** 否则页面越漂亮，误导越强。第五节那个 404 链接，就是同一批二手数据里的东西。

### 12.5 自包含 vs 可维护，选自包含

`file://` 双击打开的场景下，不能引 CDN，也不能 fetch 本地 JSON（CORS 会拦）。所以单文件是对的。

但**数据块要放在文件顶部、结构固定**，方便脚本批量替换。这次 `DATA` 硬编码在脚本中间，更新数据只能手改。

### 12.6 交付前自检四件事

1. **抽出 `<script>` 跑 `node --check`** —— 单文件 HTML 里一个语法错就是整页空白，而且报错不显眼
2. **零外部依赖** —— 全文搜一遍 `http` / `cdn`，只允许出现在超链接里
3. **窄屏不横向滚动** —— 手机上看双栏必挤，单列起步再加 `@media` 开双列
4. **每个按钮都有反馈** —— toast 或状态变化；复制类操作没反馈，用户会连点五次

### 12.7 给 agent 写文档，"禁止"比"请"有效

默认行为是"装完汇报一句都装好了"。所以指令文档里最有效的不是"请认真验证"，而是：

- 禁止跳步（失败要记录并继续，不许静默跳过）
- 禁止凭记忆拼安装命令
- 禁止直接删文件（先禁用、再卸载）

再把**输出格式**钉死（结果表 / 实际命令 / 版本号 / 失败原因 / 备份路径），拿回来的东西才可核对。

### 12.8 别把"看起来有用"当需求

第一轮 8 项全灭，根本原因是**当时没有需求**：用户只是"想看看 DSH 有什么插件"。这种状态下任何清单都会显得有用，也都会在装的时候失效。

给建议前先问一句"你最近一次觉得不方便是什么时候"，比一份 6000 条的市场导览有用。

## 十三、一句话总结

**DSH 插件生态现在处于"能用但脆"的阶段**：好东西不少（`dsh-context` 142 个版本、`dsh-todo-board` 把 peer 门做得很正规），但版本乱、同名牌多、文档滞后。

老大给的链接命中率很高（6/7），真正的瓶颈不在找得到，而在**装得上**。所以下次的重点应该从"检索"转向"版本核对 + Windows 环境排查"——这次前两轮把力气花在功能匹配上，恰恰是最不容易出错的部分。
